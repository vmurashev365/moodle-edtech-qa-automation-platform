# Test Execution Procedure

## Purpose

This document explains how to run the automation skeleton, the Phase 4 local Moodle smoke, the Phase 5 local teacher workflow, the Phase 6 local grading/gradebook workflow, and CI-safe checks.

The current framework is executable. The Phase 4 local smoke verifies the controlled Moodle login page. Phase 5 adds a teacher-facing submission review path that requires controlled seed data. Phase 6 adds one local scenario for teacher grading, gradebook row verification and backend reconciliation of the stored grade through the Moodle CLI.

## Local Setup

Use Node.js `24.x` to match the repository engine and GitHub Actions configuration.

Install dependencies:

```bash
npm install
npm run install:browsers
```

Create a local environment file:

```bash
cp .env.example .env
```

Update `.env` with any non-demo credentials, audio resource, and API token values. After seeding, run `npm run moodle:seed:env` to apply generated Moodle IDs and URLs into local `.env`.

- `MOODLE_STUDENT_ID`

- `MOODLE_SLOW_MO_MS`
- `MOODLE_STEP_DELAY_MS`
- `MOODLE_SCREENCAST` (blank by default; `true` records video and trace for every scenario. The `--screencast` runner flag sets it per run)
- `MOODLE_TRACE_MODE` (`off`, `retain-on-failure`, `on`, or `all`)
- `MOODLE_VIDEO_MODE` (`off`, `retain-on-failure`, or `on`)

Blank variables fall back to their defaults. A variable that is set to an invalid value (for example `MOODLE_TARGET_GRADE=82abc`, `UI_EXPECT_TIMEOUT_MS=10s`, `MOODLE_HEADLESS=maybe` or `MOODLE_TRACE_MODE=always`) fails with an error naming the variable instead of silently using the default.

The API token may be blank during skeleton validation. Web Service mutation and validation helpers remain pending until Moodle Web Services are configured; the Phase 6 backend check uses the Moodle CLI and needs no token.
Legacy `HEADLESS`, `TRACE_MODE`, `TRACE_ON_FAILURE`, and `VIDEO_ON_FAILURE` variables are kept only for compatibility/deprecation clarity. Prefer the `MOODLE_*` runtime variables above for new local runs and CI configuration.

## Execution Profiles

The framework has two runtime profiles:

- `demo`: headed browser, visible scenario/step terminal output, small pacing delays, and optional screencast/video with click feedback for reviewer walkthroughs.
- `fast`: headless, no artificial delays, and suitable for CI/CD validation.

The Moodle profile is named `demo` rather than production because the target is a local controlled Moodle demo instance, not a protected production or WAF-backed application.

Run local demo workflows after seeding:

```bash
npm run moodle:start
npm run moodle:wait
npm run moodle:seed:ready
npm run test:demo:smoke
npm run test:demo:teacher-workflow
npm run test:demo:grading
npm run test:demo:screencast:all
```

Scenarios that depend on the grading state begin with `Given student "…" has an ungraded submission for "…"`. That step (`src/steps/assignment.steps.ts`) runs `scripts/moodle/reset-ungraded-baseline.php` in the Moodle container, resets the student's grade to "not graded" with the same assign grading API the seed uses, reads the state back and fails the scenario if Docker is unavailable or the submission is not ungraded. Correctness therefore does not depend on feature file order. The teacher-workflow and grading demo/fast scripts still run `moodle:seed:ready` once per command so the seeded data and `.env` metadata exist.

Record visible walkthroughs:

```bash
npm run test:demo:screencast:all
npm run test:demo:screencast:grading
```

These local screencast commands force a headed browser and slower presentation pacing so the live Moodle interaction and click visualizer are visible during the run. GitHub Actions may still set `MOODLE_HEADLESS=true` when the goal is artifact capture rather than a live desktop walkthrough.

Generate an Allure report for a local review run:

```bash
npm run test:demo:grading:report
npm run test:demo:screencast:all
npm run test:demo:screencast:grading
npm run test:fast:grading:report
```

The report wrapper clears stale Allure results, runs the selected Cucumber command, generates `reports/allure-report/` even when the scenario fails, opens the local Allure viewer automatically outside CI, and returns the original test exit code. Set `ALLURE_AUTO_OPEN=false` to generate the report without launching the viewer. Moodle-specific metadata is written into `reports/allure-results/environment.properties`, `executor.json`, and `categories.json`.

Run fast checks:

```bash
npm run type-check
npm run lint
npm run format:check
npm run verify:env
npm run test:fast:api
```

## Controlled Seed Command

Create or refresh the deterministic local Moodle data:

```bash
npm run moodle:start
npm run moodle:wait
npm run moodle:seed
npm run moodle:seed:env
```

The seed runs PHP inside the local Docker Moodle container and uses Moodle internal APIs for users, course creation/update, manual enrolments, assignment creation/update, online text submission setup, and assignment grade reset. It is idempotent and does not silently edit `.env`. It writes ignored local metadata to `artifacts/seed/controlled-data.generated.json`.

`npm run moodle:seed:env` explicitly updates the untracked local `.env` from that generated artifact. If `.env` is missing, it is created from `.env.example`. If `.env` already exists, a timestamped `.env.backup.*` file is created first. The sync updates deterministic Moodle metadata from the generated `envSnippet`, including `MOODLE_STUDENT_ID`, `MOODLE_STUDENT_EMAIL`, `MOODLE_SUBMISSION_ID`, `MOODLE_ASSIGNMENT_GRADE_ITEM_ID`, and `MOODLE_ASSIGNMENT_GRADING_URL`, and preserves unrelated variables and nonblank teacher/student passwords. Blank teacher/student passwords are filled with the documented local-only demo password that satisfies Moodle password policy. Generated URLs use Moodle's configured local `wwwroot` so browser login sessions stay aligned with the running instance.

All container PHP scripts go through `src/support/moodle-cli.ts`, which runs `docker compose exec` as the Bitnami web server user `daemon`. Variables are passed by name only (`-e NAME`) with values in the child process environment, so passwords never appear in command arguments, and failure messages mask secret values. Each call has a time limit (seed 5 minutes, the ungraded-baseline reset 20 seconds, other calls 2 minutes) because the synchronous docker call blocks Cucumber's own timeouts; a timeout fails with "Timed out after N ms". Earlier versions ran the seed as root and could leave root-owned files in `moodledata`, which later breaks Moodle with "Invalid permissions detected when trying to create a directory" or "Unable to acquire a lock for caching". Repair such a volume once with `docker compose exec moodle chown -R daemon:daemon /bitnami/moodledata`, or recreate it with `npm run moodle:reset`.

`npm run moodle:seed:auth` verifies the seeded teacher and student credentials through Moodle's CLI authentication path. It runs after `.env` sync inside `npm run moodle:seed:ready` so a bad seeded password fails before browser UI steps.

The generated artifact is local setup metadata, not public proof by itself. Mission 6 Recorder/Codegen evidence is local under ignored `tools/recordings/localhost_mission6`.

Convenience readiness command:

```bash
npm run moodle:seed:ready
```

This runs seed, `.env` sync, seeded auth verification, `check:data`, and `check:grading-data` in sequence.

## Phase 5 Seed Checklist

Before running the teacher workflow, create or confirm with `npm run moodle:seed`:

- teacher user matching `MOODLE_TEACHER_USERNAME`
- student user matching `MOODLE_STUDENT_USERNAME`
- student first/display name matching `MOODLE_STUDENT_DISPLAY_NAME`, for example `Student QA`
- course `QA Automation Demo 101`
- teacher enrolment in the controlled course
- student enrolment in the controlled course
- assignment `Essay: Test Automation Strategy`
- deterministic student submission visible in the single-user grading interface opened by the assignment's `Grade` action
- Moodle user tours disabled by the seed, so the Phase 5 click path through Dashboard, My courses, course and assignment is not blocked by tour overlays

Then run `npm run moodle:seed:env` so the generated course, assignment, submissions, gradebook, and display-name values are written to local `.env`.

## Phase 6 Grading Seed Checklist

Before running the grading scenario as evidence, confirm:

- Phase 5 controlled seed checklist is complete
- deterministic `Student QA` submission appears in the single-user grading interface
- `MOODLE_ASSIGNMENT_SUBMISSIONS_URL` or `MOODLE_ASSIGNMENT_ID`/`MOODLE_ASSIGNMENT_URL` is configured
- `MOODLE_ASSIGNMENT_GRADING_URL` or enough assignment/student metadata to derive it is configured
- `MOODLE_GRADEBOOK_URL`, `MOODLE_COURSE_ID`, or `MOODLE_COURSE_URL` is configured
- assignment grade scale accepts the grade written in the grading scenario (`82`) and `MOODLE_TARGET_GRADE`, default `82`
- seed reset leaves Student QA grading baseline as not graded
- the UI scenario saves the grade written in the feature file and the gradebook displays it for the student named there; the names are resolved from `artifacts/seed/controlled-data.generated.json`
- `scripts/moodle/read-grade-state.php` (read-only, run as `daemon` with a 20-second limit) reports the same grade for the assignment and the gradebook

The seed does not pre-grade the submission with the target grade. It resets the controlled grade to Moodle's ungraded baseline through the assign grading API so the UI scenario must perform the write. Do not treat the generated local artifact as gradebook evidence.

```bash

```

```bash
npm run test:local:smoke
```

First local teacher workflow:

```bash
npm run test:local:teacher-workflow
```

Phase 6 local grading workflow gate:

```bash
npm run test:local:grading
```

Phase 7 local role-negative check:

```bash
npm run test:local:security
```

Every implemented local scenario (Phase 4 smoke, Phase 5 teacher workflow, Phase 6 grading, Phase 7 role access), after the grading data check:

```bash
npm run test:local:all
```

Suite commands prepared for later implementation:

```bash
npm run test:smoke
npm run test:web
npm run test:e2e
npm run test:security
npm run test:media
npm run test:all
```

The commands above exclude `@wip`. Every executable suite command (`test:*`, including the `local`, `demo` and `fast` variants) goes through a scenario guard (`scripts/lib/scenario-guard.ts`) that counts the selected scenarios with the Cucumber API before the run and exits non-zero when none are selected. When every matching scenario is tagged `@wip`, the error says so; today `test:media` fails this way until its scenario is implemented. `test:smoke`, `test:security` and `test:all` select the Phase 7 role-access feature and need a seeded stack. `test:wip` is the only unguarded command.

`test:local:smoke` requires the local controlled Moodle instance to be running and reachable. It does not require teacher/student/course/assignment provisioning.

`test:local:teacher-workflow` is local-only and requires the controlled seed checklist above. If data is missing, the scenario should fail with a setup blocker rather than pass.

`test:local:security` is local-only and requires `npm run moodle:seed:ready`. A signed-in Student QA opens the single-user grading URL; the scenario requires Moodle's `error/nopermission` page with HTTP 404 while the student is still signed in, and only then checks that no grade input or Save changes action is present. A redirect to the login page or another signed-in user fails it. Both scenarios need Docker for the Moodle CLI, which resets and reads the grade. A second scenario has the student send the grading panel's Save changes request (`mod_assign_submit_grading_form`) with the student's own session key; it requires errorcode `nopermissions` for `mod/assign:grade` and a stored grade that is still not graded and unchanged.

`test:local:grading` is local-only. It runs the grading data check, then the guarded Phase 6 selection. After `npm run moodle:seed:ready`, it should select one executable scenario and prove the UI grading, gradebook row verification and Moodle CLI backend reconciliation path.

`test:local:all` is local-only and requires `npm run moodle:seed:ready`. It selects `@local and not @wip` across all feature files (five scenarios today) and runs headless with the `fast` profile defaults. `test:local:screencast:all` is the screencast run without the seed; `test:demo:screencast:all` seeds and then calls it.

## Failure Evidence

For Cucumber browser scenarios, Playwright tracing starts in the Cucumber World when `MOODLE_TRACE_MODE` is not `off`. The default is `retain-on-failure`.

- `MOODLE_TRACE_MODE=off`: no trace capture
- `MOODLE_TRACE_MODE=retain-on-failure`: save `traces/<safe-scenario-name>-trace.zip` only for failed scenarios
- `MOODLE_TRACE_MODE=on` or `MOODLE_TRACE_MODE=all`: save traces for every browser scenario
- `MOODLE_VIDEO_MODE=on`: save videos for every browser scenario
- `MOODLE_VIDEO_MODE=retain-on-failure`: keep videos only for failed browser scenarios

Trace zips are ignored by git and attached to Cucumber/Allure results where the reporter supports binary attachments. Demo videos are written under ignored `videos/`, screenshots under ignored `screenshots/`, and local reports under ignored `reports/`.

## WIP / Pending Behavior

Run WIP scenarios deliberately:

```bash
npm run test:wip
```

WIP scenarios contain pending step implementations and are expected to fail with explicit pending messages. This is intentional and prevents fake-green automation. Their implemented steps (sign-in, main-menu and course navigation) run in a browser first, so `test:wip` needs the running seeded stack (`npm run moodle:seed:ready`), and each scenario stops at the step that is still pending, naming it.

## Manual GitHub Actions Workflow

The **Manual Moodle Test Run** workflow (`.github/workflows/manual-moodle.yml`) runs only on `workflow_dispatch`; it has no schedule and no pull request trigger. Every dispatch starts a fresh Docker stack and removes it, volumes included, at the end.

To dispatch it: GitHub → Actions → Manual Moodle Test Run → Run workflow, choose the branch and the inputs, then Run workflow. The GitHub mobile app offers the same form.

Inputs:

- `suite`:
  - `fast-api`: CI-safe API/environment preflight, no local Moodle Docker.
  - `local-smoke`: Phase 4 login page smoke (`test:local:smoke`).
  - `local-teacher-workflow`: Phase 5 teacher submission review (`test:local:teacher-workflow`).
  - `local-grading`: Phase 6 grading, gradebook and CLI reconciliation (`test:local:grading`).
  - `local-security`: Phase 7 role access (`test:local:security`).
  - `local-all`: every implemented local scenario, headless, no screencast (`test:local:all`).
  - `local-demo-screencast-all`: the local scenarios with screencast video and click visualizer (`test:local:screencast:all`), headless in Actions.
- `iterations` (1–5, default 1): how many times the suite runs on the same stack. Iteration 1 seeds with `npm run moodle:seed:ready` (local suites only); later iterations do not re-seed and rely on the Given step that resets a submission to ungraded. A seed failure stops the run and marks the remaining iterations as not run.
- `publish_release` (default `false`): publish the evidence as a GitHub prerelease. See below.
- `send_email`: see below.

The run step calls the same command you can run locally against a running stack:

```bash
npm run ci:moodle-suite -- --suite local-all --iterations 2
```

`scripts/run-moodle-suite.ts` runs each iteration, keeps its Cucumber JSON and Allure results under `reports/iterations/iteration-<n>/`, and writes `reports/iterations/summary.json` with the scenario and step counts per iteration. In the merged Allure report each result carries an `Iteration` parameter, an `Iteration <n>` parent suite and its own history id, so Allure lists every iteration instead of folding earlier ones into retries. The command fails if any iteration fails, runs no scenario, or exits non-zero.

After the last iteration it reads environment facts from the running stack into `reports/environment-facts.json`: the Moodle release and version through the Moodle CLI (`scripts/moodle/read-moodle-release.php`), and the image reference and registry digest of the running `moodle` container (`docker inspect`, then `RepoDigests` of its image). These are never copied from `docker-compose.yml`, because `MOODLE_DOCKER_IMAGE` can override the image; an image without a registry digest fails the run. The facts, the commit SHA, the run URL, the iteration count and the per-iteration results are added to the Allure `environment.properties`. The job summary shows a table of passed and failed scenarios and steps per iteration.

The workflow uploads `reports/`, `screenshots/`, `videos/`, `traces/` and the sanitized seed metadata as the `moodle-<suite>-evidence` artifact, on failure too, for 14 days. These artifacts are the place to debug a failed run (traces, failure videos and screenshots). They expire; the release is the durable store.

### Evidence releases

After a passed local suite (any suite except `fast-api`) the job always prepares the release assets, so a trial dispatch with `publish_release=false` shows exactly what a release would contain:

```bash
npm run evidence:package
npm run evidence:secret-guard
```

`evidence:package` (`scripts/build-release-assets.ts`) packages only runs in which every requested iteration passed, into `reports/release-assets/`:

- `allure-report.html`: the single-file Allure report (`npm run report:allure -- --single-file`). Data, scripts and the branding stylesheet are inlined, so it opens offline from `file://`; Allure's own analytics request is the only network call and is not needed to render.
- `cucumber-report-iteration-<n>.json`: Cucumber JSON per iteration.
- `environment-summary.json`: suite, commit, run URL, Moodle release and version, image reference and digest, and the per-iteration scenario and step counts.
- `video-iteration-<n>-<k>-<scenario>.webm`: `local-demo-screencast-all` only. The videos may total at most 200 MiB; a larger set fails packaging instead of publishing a partial set. The single-file report embeds the same videos again.
- `release-notes.md`: the release body (not uploaded as an asset). It states the suite, commit, Moodle release and version, image digest, iteration count with per-iteration results, the run URL, and that the run used a controlled local Docker Moodle seeded with deterministic data. It makes no claim beyond these numbers.

`evidence:secret-guard` (`scripts/check-evidence-secrets.ts`) scans every file in that folder for the actual values of `MOODLE_ADMIN_PASSWORD`, `MOODLE_TEACHER_PASSWORD`, `MOODLE_STUDENT_PASSWORD`, `MOODLE_MANAGER_PASSWORD`, `MOODLE_DB_PASSWORD`, `MOODLE_DB_ROOT_PASSWORD` and `MOODLE_API_TOKEN`, taken from the job environment and from `.env`, plus the local demo password that `apply-seed-env` fills in. It matches plain, JSON-, HTML- and URL-escaped and UTF-16 forms, decodes every embedded base64 run and unpacks zip and gzip content (Playwright traces are zips inside the base64-embedded report). Any match, any value shorter than six characters and any content it cannot unpack refuse the publish. Its output names variables, files and encodings, never a value. The release-assets artifact is uploaded only after the guard passes.

Playwright traces record typed values, including the demo password. Traces are kept only for failed scenarios in the `fast` profile, which never publish, but the screencast run records them for every scenario, so the guard refuses `local-demo-screencast-all` releases. That is intended until traces are left out of the screencast release assets.

With `publish_release=true`, the `publish-release` job runs only when the suite job succeeded and the suite is not `fast-api`. It is the only job with `contents: write`. It downloads the release assets, runs the secret guard again and creates a prerelease with the GitHub CLI:

- tag `evidence-<run id>-<run attempt>`, unique per run and attempt, targeting the tested commit (`github.sha`);
- marked as a prerelease and never as latest, with an `Evidence:` title, so it cannot be mistaken for a product version.

Releases of this private repository are visible to repository collaborators only. Record published runs in [Evidence Index](EVIDENCE_INDEX.md#controlled-moodle-evidence-releases).

The job timeout stays at 45 minutes. A local dry run of `local-all` with two iterations took about one minute after the stack was ready. Optional stakeholder email uses SMTP secrets and sends a short digest with the run link and artifact locations; large reports/videos stay in GitHub Actions artifacts.

Required email secrets when email sending is enabled:

- `MAIL_HOST`
- `MAIL_PORT`
- `MAIL_USERNAME`
- `MAIL_PASSWORD`
- `QA_REPORT_RECIPIENTS`
- `QA_REPORT_FROM`

## CI Limitations Before Moodle Workflow Execution

GitHub Actions currently validates:

- dependency installation
- TypeScript type-check
- lint script
- environment contract
- safe API preflight scenario
- report artifact upload

CI does not start Moodle, does not run `npm run moodle:seed`, does not run `npm run moodle:seed:env`, does not run WIP Moodle UI flows, does not run `test:local:smoke`, does not run `test:local:teacher-workflow`, does not run `test:local:grading`, and does not target Mount Orange. Local Moodle workflow execution remains manual until a controlled Moodle service is intentionally added to CI.

The separate manual Moodle workflow starts a controlled local Moodle container for selected local suites. It intentionally lets generated seed metadata from `.env` drive local-suite browser runs instead of keeping generated URLs or seeded teacher/student passwords as job-level environment overrides.
